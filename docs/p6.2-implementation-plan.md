# P6.2 — Lab reports and patient documents: implementation plan

Status: **preflight only.** Nothing below is applied or implemented yet.
Migration `20261021000000_patient_documents` is written but NOT applied; the
storage bucket does NOT exist; no application code uses any of it.

## Agreed decisions

1. Agreed role matrix; clinical access only for legitimate care needs.
2. Private Supabase Storage; uploads and downloads only through the server.
3. PDF, JPEG, PNG only; at most 8 MB per file; server-side content validation.
4. Archive-only in the app; retention policy to be decided before production.
5. Clinical staff may access relevant records across branches of the same
   clinic for continuity of care (doctors: their patients in any branch); other
   roles keep branch restrictions.
6. Every file view/download and every sensitive document/lab-report action is
   audited, without medical content, filenames or patient names.
7. Lab report numbering deferred.

## Permission matrix (as encoded in the migration)

| Action | Administrator | Clinic Manager | Receptionist | Doctor | Nurse | Patient (portal, later) |
|---|---|---|---|---|---|---|
| Upload administrative file (ID, insurance, consent, other) | ✓ branch scope | ✓ own branch | ✓ own branch | – | – | – |
| View administrative file | ✓ branch scope | ✓ own branch | ✓ own branch | – | – | – |
| Archive administrative file | ✓ | ✓ own branch | – | – | – | – |
| Upload clinical file / create lab report | ✓ | – | ✓ **upload-only** (own branch) | ✓ own patients, any branch | ✓ own branch | – |
| View clinical file / lab report | ✓ branch scope | – | – | ✓ own patients, **any branch** | ✓ own branch | shared, reviewed reports only |
| Enter lab values | ✓ | – | – | ✓ own patients | ✓ own branch | – |
| Review lab report | – | – | – | ✓ assigned (ordering) doctor | – | – |
| Share / unshare with patient | ✓ | – | – | ✓ assigned doctor | – | – |
| Archive clinical file | ✓ branch scope | – | – | own upload within 24 h | – | – |

"Own patients" = patients with an appointment with that doctor. "Branch
scope" = every branch for clinic-wide memberships, one branch for
branch-limited ones. Keys: new `patient_document.upload/.view/.manage`;
existing `lab_report.upload` and `lab_result.update` granted for the first time;
clinical reads use the existing `medical_record.view/manage`, `lab.manage`,
`patient.medical_record.view`, `lab_report.view`.

## Storage authorization (server)

One server-only module, `src/server/storage/documents.ts`, is the only code
that may hold a storage client (enforced by a guard test, like the existing
"server data modules never touch the mock store" test):

* `writeDocument(upload: RegisteredUpload, bytes)` — `RegisteredUpload` is a
  branded type created only from the result of
  `app.begin_patient_document_upload` (the database authorized the caller and
  returned the one storage key the server may write).
* `readDocument(doc: AuthorizedDocument)` — `AuthorizedDocument` is created
  only from a row read through RLS in the caller's tenant transaction, with
  status `AVAILABLE`. The key comes from that row, never from the request.
* No delete function in the request path. The orphan sweep (operator script)
  is the only remover.

Upload sequence: validate bytes in memory (size ≤ 8 MB, magic bytes match the
declared type, SHA-256) → `begin_…` (authorizes, registers UPLOADING, returns
key) → store object → `complete_…` (AVAILABLE + `document.uploaded`). If the
store or validation fails after registration → `fail_…` (FAILED +
`document.upload_failed`), and the object (if any) is left for the sweep.

Download sequence: one tenant transaction reads the row through RLS (invisible
or other clinic → 404, audited as `document.access_denied`), requires
AVAILABLE (archived → 410), records `document.viewed` via `app.log_event`
(disposition, category, patient id), commits; then the server fetches the
object with the secret key and streams it with `Content-Disposition`,
`X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`,
`Cache-Control: private, no-store`. A storage error after the audit commit is
recorded as `document.view_failed`.

Size: 8 MB files stay under Next 16's 10 MB proxy body buffer
(`proxyClientMaxBodySize`), which applies because `src/proxy.ts` matches `/api`.

## Failed uploads, archives, orphans

* UPLOADING rows older than 1 hour can no longer be completed; FAILED and
  stale UPLOADING rows are never listed (RLS hides them).
* Orphan sweep (`prisma/p62-orphan-sweep.ts`, operator-run, dry-run by
  default): lists storage objects without an AVAILABLE/ARCHIVED row and
  FAILED/stale rows' objects; deletes only with `--apply`. Never touches
  AVAILABLE or ARCHIVED files.
* Archived files stay in storage (retention decision pending).

## Implementation stages (after approval of the migration)

1. Apply the migration; create the bucket; run `verify-rls` (+ new checks).
2. Prisma models (`LabReport`, `PatientDocument`, enums) + `prisma generate`;
   permission catalogue entries for the three new keys and role defaults
   (must match the migration exactly); route map for `/reports`, `/documents`.
3. `src/lib/documents.ts` (pure: categories, magic-byte sniffing, filename
   sanitising, value validation) + unit tests.
4. `src/server/storage/documents.ts` (the only storage client) with an
   injectable adapter for tests.
5. `src/server/data/documents.ts` and `lab-reports.ts` (list/get via RLS,
   writes via the functions, error-code mapping).
6. Routes: `GET/POST /api/v1/patients/[id]/documents`,
   `GET /api/v1/documents/[id]`, `GET /api/v1/documents/[id]/file`,
   `POST /api/v1/documents/[id]/archive`, `GET/POST /api/v1/lab-reports`,
   `GET/PATCH /api/v1/lab-reports/[id]`, `POST …/review`, `POST …/share`,
   `POST …/unshare`.
7. UI: patient Lab reports + Documents tabs live; `/reports` worklist and
   detail live; `/documents` list live; real upload dialog; consultation
   "Add result". In live mode the fake Download/Print and the AI panel go away.
   Demo mode and the portal stay as they are.
8. Tests (below), full regression, browser checklist.

## Tests to add

* `verify-rls` (after apply, as sehat_app): no context / forged clinic /
  other clinic → 0 rows; receptionist can't read clinical rows; doctor only
  own patients (both branches); nurse own branch; Clinic Manager no clinical;
  UPLOADING/FAILED never visible; INSERT/UPDATE/DELETE denied; functions
  refuse other clinics; bucket private and no storage policies.
* Integration (rolled back, fake storage adapter): upload → list → download
  identical bytes; refusals per role; archive then download → 410; audit
  events without titles/filenames/values; branch rules; rate limit.
* Route tests: 401/403/404, invalid files (EXE renamed `.pdf`, SVG, HTML,
  empty, 8 MB + 1, type mismatch), headers, no file body on errors.
* One real-storage smoke test (upload + read + cleanup) — only with explicit approval.
* UI: live tabs never use mock data; upload validation; 403/404 states.

## Outstanding decisions

* Retention period for medical records and archived files; legal hold.
* Storage backups: Supabase Storage objects are NOT covered by database
  point-in-time recovery.
* Malware scanning (not available natively).
* Lab report numbering (deferred).
